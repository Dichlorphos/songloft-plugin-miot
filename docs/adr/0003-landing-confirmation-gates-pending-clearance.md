# ADR-0003：起播确认门控待播放上下文的清除

- 状态：已采纳
- 日期：2026-09-21

待播放上下文原本在播放指令被受理（`gracefulPlay` 返回 true）时即被清除。但「受理」只证明云端已接下请求，设备是否真的拉到流要等 10s + 8s 的起播确认才知道。于是设备没拉流时，起播失败处理会跳歌或停播，而那份本可用于重试的待播放上下文已经没了，用户再点「继续播放」只能回退到目标原上下文或收到「没有正在播放的内容」。

我们改为：下发受理后返回 `dispatched` 并保留待播放上下文，由 `PlaylistManager` 在起播确认结算时回调协调器，只有 `landed`（确认进入播放）与 `superseded`（确认窗口被暂停/切歌/停止/新内容打断，无法得出结论）才清除；`not-landed` 保留，供用户直接重试。

**为什么不阻塞到确认结束**：那会把「继续播放」响应拖到最多约 18 秒，前端按钮长时间无反馈，语音交互也不可接受。改由后台确认回调结算，响应保持即时，代价是引入一次跨模块的异步回调与「消费中」状态。

**为什么电台与单曲播放是例外**：二者在 `scheduleLandingVerify` 中不启用确认（电台长时间处于起播态、单曲没有下一首），没有可等待的结论，只能沿用「已受理下发」作为消费完成条件。此例外已写入需求规范的数据契约。

**确认窗口内重复继续**：报告 `in-progress`，既不下发也不回退，避免同一上下文被推两遍。确认窗口被后续操作打断时清除待播放上下文，而不是永久保留——用户已经用别的操作表达了对该目标的新意图，留着的旧上下文会在下次继续时把他拉回旧内容。

完整行为与验收以[需求规范](../../.scratch/playback-sync/spec.md)为准。

本决策已实现并通过自动化验证，但真机验收与发布门禁仍以[票据 03](../../.scratch/playback-sync/issues/03-manual-acceptance.md)为准；在该票据通过前，播放同步相关版本不得发布。
